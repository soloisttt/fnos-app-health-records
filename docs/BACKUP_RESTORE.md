# 备份、恢复与迁移

健康报告原件、OCR 数据和 AI 配置都属于敏感数据。备份文件应保存在可信位置，建议加密并限制访问权限。

## 应用内完整备份

进入“我的 -> 备份与恢复”，创建完整备份。备份包含 SQLite 一致性快照、报告原件、分页图、缩略图、运行配置、AI 配置及加密凭据，并提供文件大小和 SHA-256 校验清单。

恢复前应用会自动创建一份“恢复前安全备份”。上传外部备份后，先执行校验，再确认恢复。大文件下载或上传失败时，参考[常见问题排查](./TROUBLESHOOTING.md)。

## Docker 数据备份

优先使用应用内完整备份。使用 Docker 数据卷备份时，先停止应用，避免复制正在写入的 SQLite：

```bash
docker compose stop health-records
docker run --rm \
  -v fnos-health-records-data:/data:ro \
  -v "$PWD":/backup alpine:3.22 \
  tar -C /data -czf /backup/fnos-health-records-data.tar.gz .
docker compose start health-records
```

如果使用 `DATA_HOST_PATH`，停止容器后备份该主机目录即可。不要只备份 `REPORTS_HOST_PATH`，它只是外部源报告目录，不包含应用数据库和已处理结果。

## 恢复和跨设备迁移

1. 确认目标版本支持备份中的数据库 schema。
2. 为目标实例创建一份当前安全备份。
3. 使用应用内恢复，或停止 Docker 后恢复数据目录/数据卷。
4. 启动应用并检查成员、报告、原件、趋势和 AI 配置。
5. 确认无误后再删除旧实例或旧备份。

fnOS 与 Docker 使用相同的业务数据格式，但认证方式不同。飞牛完整备份迁入 Docker/本地账号环境时，预检会说明来源、档案数量和授权结果；确认恢复即将备份中的全部成员档案授权给执行恢复的管理员，之后由其通过成员共享分配给本地账号。原飞牛身份仍隔离，不启用源登录，也不将其认定为管理员本人。其他跨实例恢复继续使用受控身份映射。

### 飞牛迁入 Docker 的授权边界

- 来源通过完整备份 `manifest.json` 的 `identity.authMode=fnos` 判断，目标必须为服务端本地账号模式；文件名或容器标记不能决定授权。
- 同实例恢复保留原有权限；已知 Docker 来源跨实例恢复、迁入飞牛均不自动接管。缺少来源的旧备份仅在本地账号目标且判定为跨实例时提供未勾选的“由当前管理员接管全部档案”选项，选择后重新预检。备份来源是策略信息，不是身份证明。
- 接收者固定为执行恢复的当前有效管理员。全部档案包括回收站成员，但不改变删除状态；不合并同名成员、不更改创建者和报告归属、不继承本人关联或隐藏偏好。
- 授予管理和共享管理权限，管理员分享给其他账号后仍保留原权限；继续调整时遵循现有最后管理者保护。
- 预检令牌绑定备份摘要、操作者、目标部署、授权策略和当前身份状态，15 分钟有效且一次性执行。授权在临时数据库事务中完成并校验，任一步失败沿用安全备份及维护回滚机制。
- 确认页统一说明数据替换、安全备份和授权结果，只确认一次；完成后重新登录即可查看和分配档案，不增加登录提醒。

本次复用现有成员授权及审计结构，应用版本和 schema v17 不递增，不新增数据库迁移。

### 已恢复但看不到档案

本地管理员在“我的 → 维护工具 → 备份与恢复”可能看到“选择原始备份”入口。仅执行最近一次隔离恢复的管理员，且本地保留恢复及身份隔离记录、未映射飞牛身份、无有效共享管理者的候选档案时显示。

上传当时的原始完整备份只用于核对，不重新恢复数据。系统验证备份 ID、完整性、源身份与成员内部标识及创建者；只纳入原备份中仍未分配的档案。已经映射或已有有效共享管理者的档案跳过。核对后显示数量，一次确认并生成安全备份，在事务中补齐授权；失败不保留部分权限，成功后入口消失，可通过成员共享继续分配。

确认令牌同样绑定文件摘要、操作者、部署及当前权限状态；文件、权限或身份发生变化需重新检查。只有计数和操作信息进入提示，普通账号不能查询待处理身份和数量。缺少原始备份、恢复记录或可信关联证据时，不开放通用接管入口，继续按[身份维护工具](./IDENTITY_RECOVERY.md)逐项核验。

## 回滚限制

新版本启动后可能执行数据库迁移。回滚前必须确认旧镜像或旧 `.fpk` 支持当前 schema；不支持时不要直接启动旧版本，应使用升级前备份恢复到独立实例验证。

## 身份与授权恢复

恢复必须先预检再确认，内部备份与上传备份采用同一策略。确认凭据绑定备份摘要、当前恢复管理员、目标部署身份和已登记身份状态，15 分钟内有效且只能执行一次；备份或身份变化后重新预检。上传恢复需要预检和确认各上传一次同一文件。

- 同实例且操作者身份可验证：账号凭据、启停状态、成员授权、本人关联和隐藏偏好回到备份时点。管理员原来只有查看权限的，恢复后仍只能查看；普通账号不统一停用。当前已验证管理员的凭据和强制改密状态保留。备份后新增的账号、授权和状态可能消失，这不是合并。
- 同实例且操作者不在备份中、也没有可验证的原管理员凭据：保留独立的系统维护账号，不给其成员权限。内部身份冲突不能当作同一人。
- 其他跨实例、跨认证模式或身份无法确认（未选择上述接管策略）：源账号保留为待映射身份，旧登录不能用于目标部署；当前管理员仅保留系统维护身份。相同用户名、数值 UID 不证明同一人；fnOS 内部账号 ID 与网关 UID 已分离。
- 旧备份缺少部署元数据时，只有本地账号随机内部身份匹配，或同一内部用户 ID 与完整本地凭据均匹配，才辅助确认为同实例；其他情况默认进入隔离映射，可按上文规则明确选择管理员接管。不会依据姓名猜测身份。

对 0.2.8 等缺少部署元数据的旧备份，若恢复过程中重建过本地管理员账号，账号行 ID 可能变化。包含此修复的版本还会核对同一内部用户 ID 与完整一致的本地凭据；两者都能确认时按同实例恢复原授权。旧备份中仅用户名相同、凭据不同或内部用户不同仍进入隔离映射。跨实例恢复前自动生成的安全备份带有目标部署身份；若其中的原管理员凭据与当前管理员完全一致，可恢复该原身份及其授权。凭据不一致时继续隔离，需人工核实映射。预检会显示本次采用的策略，确认前应核对提示。

如果同实例旧版备份曾被错误隔离恢复，先保留现有数据卷和原始备份，并查找该次恢复前自动生成的安全备份。安装包含此修复的应用后，对安全备份执行预检；只有显示同实例恢复时才确认回退，重新登录并核对原账号与成员。需要再次恢复旧版备份时重新预检并核对策略。若任一步显示跨实例隔离，不要继续反复恢复，应按下文受控身份映射流程核实原账号。

目标运行目录的 `deployment-identity.json` 是本地部署锚点，不随应用内业务备份恢复覆盖。不要把整个源数据卷直接当作跨设备身份迁移；新设备应建立目标实例，再使用应用内恢复并按预检确认授权。实例标识不是凭证，也不能代替登录验证。

完整备份含数据库和密钥，持有完整备份或控制服务器的人可在应用外读取数据；管理员业务权限隔离不改变这个边界。

恢复会清除数据库中的登录会话和登录尝试，要求重新登录，不自动补建本人档案。当前版本拒绝在识别、归一化、维护、导出或其他请求尚未结束时恢复。切换前创建并验证安全备份，写入持久维护记录；文件或身份处理失败时恢复安全备份中的文件、数据库及授权。回滚失败或进程中断后保持维护状态，不开放半恢复数据。

### 跨实例映射与历史错误修复

参阅 [身份恢复维护工具](./IDENTITY_RECOVERY.md)。工具默认只读预览，需要核实源账号与目标账号实际持有人后逐项确认。映射不改写成员或报告的创建者、不移动报告、不合并同名档案；映射后在成员设置中自行确认本人关联、默认选择及个人隐藏设置。

### 恢复中断后的回滚

停止服务，保留运行目录 `restore-maintenance.json`、安全备份与 `.rollback-*` 目录。在仓库环境使用 Node 24：

```bash
node scripts/maintenance/restore-rollback.mjs --runtime /target/runtime --storage /target/archive
```

核对输出后，将本次摘要传给相同命令，并添加 `--apply --service-stopped --confirm 摘要`。工具校验安全备份、恢复数据库与文件，保留目标部署锚点与机器目录配置，成功后才移除维护标记。先在复制的数据目录验证；不要手工删除维护标记绕过恢复。

## 未完成的补充报告页

补充批次及检查点随数据库备份；文件和预览处于 reports/thumbnails，完整备份和存储迁移均覆盖。恢复继续保留原账号绑定和管理权限复核，身份待确认不会自动继续发布。已经完成的 OCR 不重复执行，AI 失败重试使用原任务检查点。详见 [补充报告页](REPORT_PAGE_APPEND.md)。

## 自动化恢复验收

服务端 `packages/server/tests/restore-takeover.test.ts` 覆盖恢复策略、权限、旧备份选择、身份状态变化、令牌篡改/过期/重放、历史修复、失败回滚及 HTTP 上传；前端 `packages/ui/tests/restore-takeover.test.ts` 覆盖一次确认、选项重新预检、失败回退和普通账号不可见。

容器端到端验收可使用仓库内的独立脚本。先启动 Docker，并准备本地已有、包含 Node 22 与 tar 的运行时镜像，例如 `fnos-health-records:test`：

```bash
GATEWAY_PREFIX=/ npm run build
npm run prepare:package
node scripts/tests/restore-docker.mjs fnos-health-records:test
```

脚本通过打包生成的飞牛网关启动器和 Unix socket 创建合成账号、成员、报告及完整备份，再通过真实 Docker 容器的 HTTP 接口验证上传预检、恢复、会话失效、重新登录、原件读取和向普通账号共享。仅使用临时目录、临时镜像和 tmpfs 数据，结束后自动清理，不访问现有数据卷，不发布镜像或应用。macOS 测试源禁用 AppleDouble 元数据，以匹配飞牛 Linux 的归档行为。

该测试验证打包启动器及真实容器中的恢复链路，不替代物理 NAS 的网关和授权目录验收；后者需要独立 fnOS 测试实例。

### 恢复后的档案分配

Docker 管理员可从备份与恢复页面的“管理账号”进入本地账号管理，再通过“分配档案”进入家庭成员设置共享权限。授权列表同时显示名称与登录用户名，便于区分同名账号；单次和批量确认均标明接收账号与档案范围。取消确认不会改变授权，失败时保留原权限显示。

历史档案权限检查失败时，页面提供“重新检查”，无需重新恢复备份；检查失败不代表没有待处理档案。接管仍需核对原始备份及确认，不增加重复弹窗。

## 反馈安装身份

反馈安装身份保存在数据库 `app_settings` 的内部键 `x-client-id` 中，首次使用反馈接口时通过 32 字节安全随机数生成，编码为 43 位 Base64URL。不会在应用启动时生成或上报，仅通过需登录且禁止缓存的反馈身份接口提供给浏览器，用于反馈请求头；不写入日志或公开诊断。

完整备份包含该身份。恢复时优先使用备份中的身份；旧备份没有该字段时保留目标应用已有身份，两边都没有则等待首次使用反馈功能生成。损坏的身份不会静默重置。将同一备份恢复到多个实例会共享反馈记录；该身份与用于本地账号权限隔离的部署身份不同，不改变 fnOS / Docker 鉴权。

备份中包含反馈访问凭证，应按完整应用备份保管。不要公开分享备份或内部配置值。
